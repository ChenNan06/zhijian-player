## 1. 四条架构红线，以及它们各自的落地方式

用户给了四条"绝不妥协"的红线。每一条都对应一个具体的技术选择，而不是一句口号。

### 红线 1 — 绝对单一渲染管线（严禁多窗口飞线互追）

**要求**：不许用独立顶层窗口做控制栏/标题栏，不许用定时器追踪主窗口位置；
视频必须与 UI 在**同一原生窗口、同一渲染上下文**里，GPU 层面原子同步。

**做法**：用 `mpv_render_context`（`MPV_RENDER_API_TYPE_OPENGL`）把视频帧渲染进
`QOpenGLWidget` 的 FBO，与其它 Qt 控件在**同一次 backing-store 合成**里上屏。

**为什么不用"把 mpv 的 HWND 塞进 Qt"（`wid=` 方案）**：
`wid` 方案下视频面是一个**原生子窗口（native child HWND）**，Windows 规定它永远盖在
父窗口的 Qt 控件之上 —— 想在其上浮一层半透明控制条，就只能再开一个独立顶层窗口，
于是拖窗口/缩放时两者必然错位。这是结构性的，不是调参能解决的。

**踩坑记录**：

| 坑 | 现象 | 根因 |
|---|---|---|
| 给 `QOpenGLWidget` 设了 `WA_NativeWindow` | mpv 明明在画（`rendered_frames` 一直涨），屏幕上却**一片纯黑** | 它变成了独立原生子 HWND，Qt 的合成路径失效 |
| `wglGetProcAddress` 只查第一次 | `mpv_render_context_create` 返回 `-18 not supported` | GL 1.1 的核心函数（如 `glClear`）它一律返回 NULL，必须回落到 `GetProcAddress(opengl32.dll, ...)`；而 `GetProcAddress` 在 **kernel32** 不在 opengl32 |
| `FLIP_Y` 取值 | 画面上下颠倒 | QOpenGLWidget 的 FBO 需要 `flip_y = 1` |
| Qt 控件与 GL 控件叠放 | — | 用 `QGridLayout`：GL 控件跨全部行列、`QSizePolicy.Ignored`；浮层占单独的行,col 相同，后 add 的天然在上层。**全程零 `setGeometry`** |

### 红线 2 — 彻底消灭绝对坐标（流式弹性布局）

全项目 **grep 不到一处 `y += 30` 或手工 `setGeometry`**（唯一两处 `setGeometry` 是
拖放高亮层跟随父控件尺寸，属于"复制父矩形"而非坐标计算）。

设置面板的可用空间是**算出来**的，不是写死的：
`_fit_settings()` 先按理论值设置尺寸，再用**实测几何**迭代收敛 —— 因为布局器给出的
实际可用高度受各处 margin/间距影响，纯算会差几像素，而差几像素就会压到控制条上。

> 这个坑真实发生过：`setFixedSize` 定的是**含阴影外框**的整控件尺寸，
> 只把 body 卡在可用高度上，结果整个面板比舞台还高 38px，直接盖到控制栏上。
> 像素自审把它读成了"面板大面积与视频串色"。

### 红线 3 — 单例生命周期与进程退出闭环

* **探针实例**：`shared_probe()` 进程内共享一个 mpv 实例，选项里永久写死
  `audio=no / video=no / aid=no / vid=no / ao=null / vo=null`。既不可能发出第二个声音，
  也不会出现"短命 mpv 实例秒建秒销导致 libmpv 内部异常穿透"的偶发崩溃。
* **退出顺序**（`MainWindow.closeEvent` + `app.aboutToQuit`，严格反序）：

  ```
  停所有定时器
    → 落盘（播放进度 / 窗口几何 / 配置）
    → 停时长探针线程
    → **在 GL 上下文仍可用时** 清回调 + mpv_render_context_free
    → mpv: vid=no + stop → 事件线程置停机标志 + wakeup → join
    → 让 Qt 正常拆窗口
    → aboutToQuit: mpv_terminate_destroy → 关探针 → flush 日志(不 close)
  ```

  **不使用 `TerminateProcess`**。实测 10 轮"启动→播放→关窗"：10/10 干净退出（码 0），
  进程 0.5~1.1 秒内从任务管理器消失，零崩溃。
  （对比：上一代用 `wid` 嵌原生子窗口的方案，正常退出约有 1/3 概率崩在 libmpv 内部 ——
  因为 VO 线程还在引用一个已经被 Qt 销毁的 HWND。渲染 API 方案里 mpv **从不接触任何 HWND**，
  这个崩溃源在结构上就不存在了。）

* **单实例**：`QLocalServer` 命名管道。第二个实例连上后发 `SHOW`，已有实例置前后新实例退出。

### 红线 4 — 侧滑抽屉与一体化交互

播放列表是**主窗口布局内的一格**（`QHBoxLayout` 的内容行右侧），不是浮层、不是顶层窗口。

> 因此"播放列表背景向下穿透切断底部控制栏"在**结构上就不可能发生** ——
> 抽屉和胶囊是同一个 `QVBoxLayout` 里的上下两个兄弟，抽屉的底边天然就是胶囊的顶边。
> 实测拉伸全程两者偏差 **0px**。

## 2. 关键设计决策

### 2.1 为什么硬件解码是 `nvdec` 而不是 `d3d11va`

`mpv_render_context` 的 OpenGL 后端在 Windows 上有两条零拷贝路径：

| hwdec | 要求 | 本机实测 |
|---|---|---|
| `d3d11va`（零拷贝） | GL 上下文必须是 **ANGLE**（EGL 包装 D3D11），才能做 D3D11↔GL 纹理互操作 | ❌ `hwdec-current` 直接变成 `no` |
| `nvdec` | CUDA-GL 互操作，NVIDIA 显卡 + 桌面 WGL 即可 | ✅ `hwdec-current = nvdec` |

所以配置里写的是 `hwdec=auto-safe`（跨机器安全），在本机自动解析为 `nvdec`。
启动探针脚本 `scripts/10-probe-gl-mpv.py` 会逐个候选试一遍并打印结果，
**不靠猜**。

### 2.2 两段式 Seek：拖动走关键帧，松手才精确对位

```python
拖动中 → seek <t> absolute+keyframes   # 对齐关键帧, 不回溯解码
松开   → seek <t> absolute+exact       # 帧级精确
```

并且**用 `mpv_command_async` 下发** —— 同步版 `mpv_command` 对 seek 会阻塞到
demuxer + 解码器重置完成（4K 下实测约 65ms）。在 GUI 线程里同步发 seek，
拖动进度条时界面会一顿一顿的（每 80ms 卡 65ms）。

另外把 `swapInterval` 设为 0：视频已经在 FBO 里画好了，再等一个垂直同步
只会白白加上最多 16.7ms 的"画面恢复延迟"。

### 2.3 长按倍速

```
右方向键 keyPress（非自动重复）
    → 记 _right_down = True, 启动 300ms 单次定时器
定时器到点且仍按住
    → 平滑切到配置倍速（默认 2.0x）
keyRelease
    → 若在加速态: 立即恢复 1.0x
    → 否则: 相对跳转 +5 秒
```

两个必须做对的地方：

1. **自动重复事件必须整体忽略**。按住键时 Windows 会以 ~30Hz 发 WM_KEYDOWN，
   Qt 把它们标成 `isAutoRepeat()`。如果不拦，按住右键会一边加速一边疯狂 +5 秒跳。
2. **快捷键必须挂在应用级事件过滤器上，不能只覆写 `MainWindow.keyPressEvent`**。
   按键先送给**焦点控件**：抽屉里的搜索框（QLineEdit）会吃掉方向键。
   实测症状极其迷惑 —— **只有 keyRelease 冒泡到了主窗口，keyPress 被吃掉**，
   表现成"单击还能快进、长按死活不出倍速"。
   事件过滤器在事件到达目标控件**之前**看到它，是唯一可靠的位置。

### 2.4 无边框窗口的缩放：交给系统，不要自己驱动

```python
showEvent → 补 WS_THICKFRAME
WM_NCCALCSIZE → 返回 0（客户区 = 窗口矩形）；最大化时贴显示器工作区
WM_NCHITTEST  → 边缘返回 HTLEFT/HTRIGHT/...，标题栏空白返回 HTCAPTION
```

系统接管后顺带白送 Aero Snap 与 Win11 的贴靠布局（最大化按钮返回 `HTMAXBUTTON`）。
**不用**"开个定时器读全局光标再 setGeometry"那套 —— 那是"拉边框不动/只在没有子控件的
那一侧拉得动"的经典根因。

> ⚠️ `WM_NCCALCSIZE` 里**绝不能调 `win.winId()`**。首次 `WM_NCCALCSIZE` 发生在
> `CreateWindowEx` 完成之前，那时调 winId() 会让 Qt 递归地再去创建平台窗口，
> 结果是 CreateWindowEx 失败并无限重试 —— 窗口根本出不来，日志刷屏
> `Failed to create platform window`。要用消息里的 `msg.hWnd`。

### 2.5 三合一媒体路由

三种媒体共用**同一条渲染管线**（包括图片）：

| 类型 | 走法 | 界面差异 |
|---|---|---|
| 视频 | mpv 正常播放 | 时间轴 + 完整控制条 |
| 图片 | mpv `image-display-duration=inf` + `loop-file=inf`；缩放走 `video-zoom`（log2 尺度）、平移走 `video-pan-x/y`、旋转走 `video-rotate` | 隐藏时间轴；顶部浮出缩放/旋转工具条 |
| 音频 | mpv 播放音频；**`loadfile` 时带 `vid=no` 关掉视频输出**（含 mp3 内嵌封面流） | 隐藏画面相关按钮；中央浮出专辑封面卡片 |

音频的封面与标签由自写的纯 Python 解析器（`media/tags.py`）从
ID3v2 APIC / FLAC PICTURE / MP4 covr / Ogg Vorbis 里直接读出，
**不需要 ffprobe、不需要额外进程**，也绝不与 mpv 的画面重影。

> `vid` 这类属性会被 mpv 按文件重置，所以必须在 `loadfile` 的那一刻作为
> **逐文件选项**一起给（`loadfile <url> replace -1 "vid=no"`），否则"设了等于没设"。

### 2.6 时长探针

播放列表里每个条目的时长由后台线程用**共享探针实例**顺序补齐（`media/prober.py`），
一次只探一个文件，列表被替换/程序退出时立即放弃。
探针永久带 `audio=no` —— 从机制上杜绝"双声事故"。

## 3. 为什么留了一个"控制面"（`src/zhijian/ipc.py`）

验收要求"不能用虚拟事件自欺欺人"。真实输入注入（SendInput）能解决**怎么操作**，
但解决不了**怎么断言** —— 光看截图猜状态是不可靠的。

`ControlServer` 是一个命名管道上的 JSON 控制面，只做两件事：

1. 让测试脚本能**读回真实状态**：渲染帧计数、丢帧计数、`hwdec-current`、
   每个控件的窗口内坐标、键盘事件环形缓冲、逐次 resize 的几何时间线；
2. 让测试脚本能**切场景**（打开文件 / 开抽屉 / 开设置 / 全屏）以便截图自审。

它**不参与产品逻辑**，只在显式传 `--control <name>` 时启动。

事实证明它是这个项目里性价比最高的一块代码 —— 上面"踩坑记录"里至少一半
（delegate 绘制异常被吞、时间文字永远 00:00、vid 没生效、面板溢出）
都是靠它一眼定位的，否则每一个都要靠"看截图猜"。

## 5. 第二轮修复：用户实测反馈的 5 个问题

第一版交付后用户逐条实测，报了 5 个问题。每一条的**真因**都和表象差得很远，
记在这里，因为它们都属于"看起来是 A、其实是 B"的类型。

### 5.1 所有小图标都被截掉一块（X 号少一笔、播放键缺角、截图键断边）

**真因**：`QPixmap` 调过 `setDevicePixelRatio(dpr)` 之后，**`QPainter` 的坐标系就已经
按 dpr 缩放好了**。而渲染时又传了物理尺寸的矩形：

```python
px = QPixmap(size * dpr, size * dpr)
px.setDevicePixelRatio(dpr)
renderer.render(painter, QRectF(0, 0, size * dpr, size * dpr))   # ← 画了两遍 dpr
```

结果只有左上角约 `1/dpr²` 的区域落在 pixmap 内，右边和下边整片被裁掉。
正确写法是传**逻辑尺寸** `QRectF(0, 0, size, size)`。

> 之所以一直没发现：我自己写的图标检查脚本是把 SVG 直接画在 sheet 的 painter 上，
> **绕过了 `render_pixmap` 这条真实路径**。修完后专门写了 `scripts/_iconclip.py`：
> 45 个图标 × 3 种 DPR = 135 个渲染，逐个检查四条边有没有像素溢出。
> 修复前 **87/135 中招**，修复后 0/135。

同一个毛病还有第二处：音量条的轨道横跨整个控件宽度，拉到 100% 时圆点圆心正好落在
右边界上，右半个圆被裁。修法是轨道左右各内缩一个圆点半径。

### 5.2 播放列表的收起按钮是摆设

**真因**：点收起按钮时鼠标**本来就停在右边缘**，"鼠标碰到右边缘自动展开"的逻辑
在 120ms 后立刻把抽屉又弹了回来。

修法两条：
1. 显式收起之后进入**抑制态**：指针必须先离开右边缘热区，再重新靠近才会自动展开。
2. 按爱奇艺的做法，在画面右边缘加一个**常驻的展开手柄**（20×74 的圆角小标签），
   不依赖"碰边缘"也能打开列表。

### 5.3 在设置界面里滚轮会调音量，还把设置面板挤下去

两个独立问题：

* **滚轮**：`QScrollArea` 滚到顶/底之后会把 wheel 事件**忽略掉**，它冒泡到主窗口，
  主窗口就当成"调音量"处理了。修法是在 `wheelEvent` 里先判断指针是不是落在
  设置/字幕/抽屉上，是就 `ignore()` 交回给面板。
* **面板被挤**：OSD 原本放在底部浮层那一行的布局里，它一出现就把第 2 行从 14px 撑到 44px，
  网格只好从设置面板所在的行扣掉 30px。修法是让 OSD 和视频**共用 (0,0,3,1) 这个跨三行的大格**
  —— 该格子的尺寸早已被视频撑满，OSD 再高也不会改变任何一行的分配。

### 5.4 启动慢 + 拖动音量条/进度条很不跟手

**真因是同一个，而且完全不在意料之中**：事件线程在 `mpv_wait_event()` 这种**阻塞调用**
外面一直握着句柄锁。UI 线程每次写属性/发命令都要等它超时，**实测每次 ~110ms**。

* 启动时写 12 个字幕样式属性 + 音量 → **1.8 秒**的纯等待；
* 拖动音量条每移动一像素写一次 → 每一像素卡 110ms。

修法只有一行：`wait_event` 里**取到句柄指针后就放锁**再调用阻塞函数
（`mpv_wait_event` 本来就只允许单线程调用，我们的设计里只有事件线程会调它）。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 启动到窗口可见 | ≈ 2900 ms | **≈ 830 ms** |
| 单次写 volume | ~110 ms | **0.01 ms** |
| 进度条单次预览 seek | ~65 ms | **11.8 ms** |

顺带把 GL 上下文（视频面）从 `show()` 里挪到窗口显示之后 —— 用户先看到完整界面，
画面晚 116ms 跟上，而不是干等三秒黑屏。

> 排查手法上值得记一笔：一开始靠"感觉"猜是 `show()` 慢，加了分阶段打点才发现
> `show()` 只占 567ms，剩下 1.8 秒全在**它前面那几行同步写属性**上。
> 后来用 `cProfile` 覆盖到 `show()` 为止，看到 `show` 的 tottime 只有 0.4 秒 ——
> 才把注意力转到别处。**先测量，再优化**，这次省下的时间远超打点本身。

### 5.5 落地页引导文字被"水平腰斩"

**真因有三层，缺一不可**：

1. `EmptyState` 被父布局用 `Qt.AlignHCenter` 放进去，**只能拿到自己的 sizeHint 宽度**
   （实测 270px），副标题的 `maximumWidth(620)` 根本没机会生效，文字被挤成 4 行；
2. 普通 `wordWrap=True` 的 QLabel，其 `minimumSizeHint()` 非常小（"反正能换行"），
   布局器于是有权把它压到比实际文字还矮 —— 压下去就是"腰斩"；
3. 容器高度 240px 而 sizeHint 是 274px，差 34px 正好一行。

修法：给容器钉死宽度区间 `[560, 660]`；引入 `WrappedLabel`（按父容器宽度用
`heightForWidth()` 算出真实高度并顶进 `minimumSizeHint`，布局器再也压不动）；
副标题拆成两行短句；"最近打开"改成**可选装饰**，高度不够时优先砍它。

> `WrappedLabel` 里有个细节：参考宽度要取**父容器**的宽度，不能取自己的 `width()`。
> 用自己的宽度会来回震荡（按旧宽度量出 2 行 → 给 34px → 下一轮按新宽度只算 1 行 → …）。

## 6. 第三轮修复：全屏黑屏 / 卡顿 / 换肤（用户实测）

### 6.1 ⚠️⚠️ 一行 Win32 代码把窗口尺寸永久钉死在旧值

`WM_NCCALCSIZE` 是无边框窗口的标准拦截点。我写成了：

```python
params.rgrc[0] = params.rgrc[1]      # ← 灾难性的一行
```

`wParam = TRUE` 时系统给的三个矩形是：

| 字段 | 真实含义 |
|---|---|
| `rgrc[0]` | **系统算好的新窗口矩形**（要返回的就是它） |
| `rgrc[1]` | 移动/缩放**之前**的窗口矩形 |
| `rgrc[2]` | 移动/缩放之前的客户区矩形 |

`rgrc[0]` 本来就已经是"新窗口矩形"，**什么都不用改，直接返回 0 就是无边框**。
赋成 `rgrc[1]` 等于每次把客户区退回旧尺寸 —— 实测窗口 1200×900 时 `GetClientRect`
报 **2380×1330**。Qt 的窗口几何是从客户区算的，于是：

* 全屏后原生窗口已是 2560×1600，**Qt 永远以为自己是 1280×760**；
* 视频层只铺左上角约 3/4，右边和下边一片黑；
* 最大化同样；从别的应用切回来必黑屏（重画的还是那个错的客户区）。

**定位手法**：加 `ZHJ_NO_NATIVE=1` 把整个 `nativeEvent` 关掉做 A/B —— 全屏立刻正常，
一步锁定"是自己拦的 Win32 消息"，再二分 `ZHJ_NO_NCCALC` / `ZHJ_NO_HITTEST` 确认是哪条。

### 6.2 抽屉改成覆盖层：动画不再重排整个窗口

抽屉原本和舞台是同一行的兄弟，展开动画每一帧改宽度 ⇒ 整窗 relayout（**26.7ms/帧**）
+ `QOpenGLWidget` 重新分配 FBO，实测只有 11fps。

改成挂在舞台跨行格子里的**覆盖层**（右对齐，`minimumWidth = 0`）后：
动画只改一个 `slot` 的宽度，抽屉自己保持目标宽度被裁切 —— 抽屉内部一次布局都不跑，
**视频控件尺寸一格不动**。事件循环最大间隔从 >150ms 降到 38ms。

> `minimumWidth` 必须是 0，否则抽屉宽度会顶进格子的最小尺寸，又开始推动视频。

### 6.3 pixmap 缓存要按**字节**限流，不能按条目数

16 层弥散阴影每帧画 16 个抗锯齿圆角矩形，胶囊一次重绘 **3.08ms**；
整体缓存成 pixmap 后降到 **0.65ms**。但第一版按"最多 8 条"限流 ——
一张抽屉大小的背景就是 ~2MB，上限 16MB，且尺寸一变就 churn 一次分配/释放。
**实测峰值高水位因此每轮涨 ~1MB**，差点被当成新的内存泄漏。
改成"总量 6MB + 单张超 2MB 不缓存"后，末 10 轮峰值极差 **0.0MB**。

### 6.4 换肤：从"连不上任何东西的下拉框"变成真会换

设置面板里原本的"强调色"`QComboBox` 列了 5 个颜色名，**选了什么都不会发生**。
现在是 5 套主题预设（强调色 + 玻璃底色一起换）+ 色块按钮 + 运行时套用：
`theme.apply_theme()` 原地改调色板 → `app.setStyleSheet(build_stylesheet())` →
自绘控件显式 `update()` → 落盘。图标缓存按颜色做 key，换色后自然不复用旧缓存。

### 6.5 布局：视频铺到窗口底、控制条浮在画面上、抽屉不切断它

网格改成 4 行：顶部浮层 / 中部 / 底部 / **控制条区**。

* **视频跨全部 4 行** → 一直铺到窗口底，不再"卡在控制条上面"；
* **胶囊浮在第 3 行** → 无操作时淡出，露出的是完整画面，没有"视频被压缩"的割裂感；
* **抽屉跨 0..2 行** → 底边精确落在胶囊顶边，仍然不会向下穿透切断控制栏。

判据（`scripts/49-accept-ui-round3.py`）：
`video_bottom == capsule_bottom`、`drawer_bottom == capsule_top`、`drawer_right == window_right`。

### 6.6 图标语义

`settings` 图标原来是"圆 + 六条放射线"—— 那正是**亮度/日夜切换**的图形语言，
用户一眼就认错了。换成六角螺母轮廓 + 内圈 + 六根短齿才读得出是齿轮。

## 7. 已知限制与取舍

* **只支持 Windows**：用了 DWM 圆角、Win32 无边框命中测试、SendInput 验收。
  跨平台需要替换 `platform/win.py` 与 `_wininput.py`。
* **`hwdec` 走 GL 后端时 `d3d11va` 不可用**（需要 ANGLE 上下文）。
  在 AMD/Intel 机器上会自动退化到 `d3d11va-copy` 或软解 —— 仍然可播，只是不是零拷贝。
* **控制条是悬浮胶囊，不是老版的贴底通栏**。这是**刻意的现代化偏离**：
  用户明确要求"悬浮胶囊 + 微冷色通透底色 + 0.5px 内发光折射高光边框 + 柔和弥散阴影"，
  与老版的"通栏直角纯黑"是两回事。比例（高度占窗高、按钮间距、内边距）仍按逆向值继承。
* **精确 Seek 偶发 150~300ms 抖动**：来自磁盘/调度，不是解码瓶颈；
  拖动路径（关键帧跳转）P90 稳定在 100ms 以内。
* **程序化的 `QWidget.move()` 在无边框窗口上不可靠**：实测它会让 Qt 缓存的尺寸与
  Windows 原生窗口的实际尺寸**失步**（Qt 侧 800×600、原生跳回 1920×1140，且之后
  Qt 认为"尺寸没变"不再下发 SetWindowPos）。真实用户拖标题栏走的是系统模态循环，
  不受影响。项目内统一改用 `platform/win.move_window()`（原生 `SetWindowPos` + `SWP_NOSIZE`），
  恢复窗口几何时用一次性的 `setGeometry(x, y, w, h)` 而不是 `resize()` + `move()`。

## 8. 第四轮：把 GUI 线程从 mpv 手里抢回来

### 8.1 现象与排除

用户："播放时拖动窗口、来回拖进度条音量条、展开播放列表，任何与动画有关的东西都会掉帧。
为什么爱奇艺万能播放器就不会？"

实测 `mpv_render_context_render()` **单帧 26.3ms**。逐条排除：

| 猜测 | 实测 | 结论 |
|---|---|---|
| 缩放器太贵 | `bilinear` 26.52ms | ✗ |
| 硬件解码互操作同步 | 冷启动建链：nvdec 26.73 / nvdec-copy 26.72 / **纯软解 26.21** | ✗ |
| 色彩管理 / deband | 全关 + `profile=fast` 26.36ms | ✗ |
| 输出分辨率 | 798×512 → 29.47ms，1278×712 → 25.93ms | ✗ |
| 垂直同步 | 全局 `swapInterval=0` 26.46ms | ✗ |
| Qt/驱动的每帧开销 | **空的 QOpenGLWidget 的 paintGL 只要 0.02ms** | ✗ |
| GL 函数加载器回调 | 渲染期间回调 0 次 | ✗ |

**成本对一切参数完全不敏感** —— 这个形状不像"计算"，像"等待"。

### 8.2 真因

mpv 渲染 API **默认开启 `MPV_RENDER_PARAM_BLOCK_FOR_TARGET_TIME`**：
`mpv_render_context_render()` 会阻塞到这一帧的目标显示时刻才返回。
26ms ≈ 33ms 帧间隔 − 约 7ms 实际渲染工作。**它不是忙，是在睡。**

```python
block = c_int(0)
params[2].type = MPV_RENDER_PARAM_BLOCK_FOR_TARGET_TIME
params[2].data = ctypes.cast(byref(block), c_void_p).value
```

帧的节奏本来就该由 mpv 的 update 回调 + Qt 的重绘驱动，不需要在 render 里再等一次。

### 8.3 结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `mpv_render_context_render` 单帧 | 26.30 ms | **1.05 ms** |
| 事件循环 p50 | 33.4 ms | **20.0 ms** |
| 事件循环最大间隔 | 36.2 ms | **23.5 ms** |
| 3 秒内事件循环圈数 | 92 | **150** |

### 8.4 三条方法论

1. **"固定成本、与所有参数无关"要读成"在等什么"，不要读成"算得慢"。**
   算力成本一定随分辨率/算法变化。
2. **隔离到地板再下结论**：写一个什么都不画的 `QOpenGLWidget` 量它的 `paintGL`。
   0.02ms vs 26ms 一出来，"Qt/驱动不行"和"mpv 慢"同时被排除，只剩"mpv 在等"。
3. **热改属性验证不了启动期配置**：mpv 对已加载的文件不会重开解码链，
   播放中 `set_property("hwdec", ...)` 测出来的数是无效的。必须"先起空实例 →
   设属性 → 再打开媒体"。**这一条差点让我得出错误结论，并为此上一场没必要的大改造。**
